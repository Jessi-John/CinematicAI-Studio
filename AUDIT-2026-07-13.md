**Date:** 2026-07-13
**Scope:** Full repository audit of `D:\youtube` (CinematicAI Studio — Next.js 16 frontend + Express/Prisma/BullMQ backend). Every non-test source file and config read line-by-line; test suites statically reviewed and executed.
**Methodology contract:** evidence-only — every finding cites file:line verified by direct read; first-pass subagent claims re-verified before inclusion; false claims retracted (see §12).

## Verdict: NOT production-ready

Six independently-verified production blockers: story regeneration throws 500 on an FK constraint (core feature dead), DLQ-restarted jobs can never succeed, the backend test suite is red, both backup scripts fail by construction, CI fails every push to `main`, and the `E2E_TEST` auth-bypass cluster is ungated by `NODE_ENV`.

## 3. Critical findings (production blockers)

### C1. Story regeneration 500s — FK violation in `replaceStoryAtomically`
- **Where:** `backend/src/database/prisma-storage/write.ts` (`replaceStoryAtomically`); FK defined in `backend/prisma/migrations/20260521165856_add_character_bible_fields/migration.sql` (`generation_logs_storyId_fkey`, immediate, ON DELETE SET NULL).
- **Root cause:** the transaction does `tx.generationLog.updateMany({ storyId: oldStoryId } → newStoryId)` **before** `tx.story.create()` for the new story. The immediate FK rejects the update when the old story has ≥1 generation-log row and the candidate id ≠ old id — always true, since `buildStoryFromEpisodes` assigns a fresh `randomUUID()` and `regenerateStory` passes `persistMode: 'return-candidate'` (`backend/src/routes/story-regeneration.ts:70`).
- **Impact:** `POST /api/stories/generate/:id/regenerate` returns 500 (P2003) for any previously-generated story. Core feature dead.
- **Fix:** create the new story row first (or defer the constraint), then move the logs; keep delete-old/create-new ordering consistent with `write.test.ts` expectations.

### C2. DLQ restart is a guaranteed death-loop; DLQ list is unreadable
- **Where:** `backend/src/routes/admin.ts:244-254` (restart drops `userId`), `backend/src/queue/workers/pipeline/index.ts:378,462` (`userId: 'unknown'` fallback), `backend/prisma/migrations/20260629120000_require_story_userid/migration.sql` (`stories_userId_fkey` RESTRICT).
- **Root cause:** restart re-enqueues without `userId` → pipeline substitutes `'unknown'` → `createStory` violates the RESTRICT user FK → job fails → re-DLQ, forever.
- **Compounding defects:** `GET /api/admin/dlq` reads Redis list `['failed']` while entries are written under `'waiting'` (`admin.ts:539-540`) → the DLQ list is always empty; entries never expire; no DLQ worker exists. `POST /dlq/:jobId/requeue` (`admin.ts:603`) and `DELETE /dlq/:jobId` (`admin.ts:652`) have **zero tests**.
- **Impact:** the DLQ is both invisible and unrecoverable; poisoned jobs loop forever consuming worker capacity.
- **Fix:** persist original job data (incl. userId) in DLQ entries; read the correct list key; add TTL; add requeue/delete tests.

### C3. `E2E_TEST` bypasses ungated by environment
- **Where:** `backend/src/middleware/jwt.ts:55,204-206` (auth + transport skip), `backend/src/middleware/csrf.ts:137`, `backend/src/middleware/rate-limit.ts:214-218,249-251`, `backend/src/queue/workers/pipeline/index.ts:134-135`, `backend/src/lib/ai-client.canned.ts:341-343` + `backend/src/lib/ai-client.ts:963` (`isCannedMode`).
- **Root cause:** every gate checks only `process.env.E2E_TEST === 'true'` (or `STORY_TEST_MODE=canned`) with no `NODE_ENV !== 'production'` conjunct. `docker-compose.e2e.yml:11-19` isolates the vars to the e2e override (verified: prod compose has no E2E vars), but the code-level gates remain unguarded.
- **Impact:** any leak of `E2E_TEST=true`/`STORY_TEST_MODE=canned` into a production environment disables auth, CSRF, rate limits, and swaps live AI for canned responses.
- **Fix:** require `NODE_ENV !== 'production'` (or explicit `ALLOW_E2E=1`) in every gate; extend `test-quality/env-leak-invariants.test.ts` to cover the new guard.

### C4. Both backup scripts fail by construction
- **Postgres — `deploy/backup/backup-postgres.sh:121`:** the verify container overrides the postgres image entrypoint with `bash -c "… pg_isready …; createdb …; gunzip | psql …"`. The postgres `docker-entrypoint.sh` execs non-`postgres` commands directly, so **no server ever starts**; `pg_isready` fails under `set -e` → restore verification can never pass → script exits 1 **before the retention section runs**. Nightly "backup failed" alerts + unbounded backup growth. Additionally `backup-postgres.sh:101`'s dump-content check is dead code: `if ! (gunzip -c … | head -10 | grep -q "PostgreSQL database dump" || true)` — the `|| true` inside the negated pipeline makes it always succeed.
- **Redis — `deploy/backup/backup-redis.sh:71,76,87`:** `TMP_RDB="/tmp/redis-${TIMESTAMP}.rdb"` is created **inside the container** via `docker exec … redis-cli --rdb "$TMP_RDB"`, but `gzip -9 -c "$TMP_RDB" > "$BACKUP_FILE"` runs on the **host**, where the file never exists (missing `docker cp`) → compression step always fails. (The redis *verify* container is correct — it starts `redis-server` itself.)
- **Cron chaining:** `backup-postgres.sh … && backup-redis.sh` — the postgres failure suppresses the redis attempt entirely.
- **Fix:** run postgres verify with a real temp server (or `pg_restore --list`); `docker cp` the RDB out before gzip; remove `|| true`; decouple the two cron jobs.

### C5. CI fails every push to `main`; validate-prod-env test is vacuous
- **Where:** `.github/workflows/ci.yml:17` (`commitlint` job gated on `github.event_name == 'pull_request'`) + quality-gate job (`if: always()`, requires `needs.commitlint.result == "success"`).
- **Root cause:** on push, commitlint is `"skipped"` ≠ `"success"` → gate exits 1 on every main build.
- **Also:** `ci.yml:512` validate-prod-env passes on **any** `EnvValidationError` (it logs `e.envName` but never asserts it is the placeholder var) and relies on Node ≥20.19 `require(ESM)`.
- **Fix:** accept `"skipped"` in the gate expression; assert the specific env var name in the validate-prod-env output.

### C6. Backend test suite red — `race.stories.test.ts` broken
- **Where:** `backend/src/queue/workers/race.stories.test.ts` (mock at line ~31: `$transaction: vi.fn()`); production code `backend/src/database/prisma-storage/write.ts:41` wraps create in `prisma.$transaction(...)`; failure surfaces at `converters.ts:155`.
- **Root cause:** the mocked `$transaction` returns `undefined` and never invokes its callback → `story.create` inside the transaction never runs → `createStory` returns `undefined` → `convertStory(undefined)` throws. The file's header comment claims "createStory does not use `$transaction`" — stale premise. 5/5 tests fail.
- **Fix:** make the mock invoke its callback with the mocked tx, or delete the file (remaining assertions duplicate `prisma-storage.test.ts`).

## 4. High findings

### H1. SSE job-stream IDOR
- **Where:** `backend/src/routes/events.ts`; `backend/src/middleware/api-auth.ts:42-51` (`verifySSEAuth`).

## 14. What fixing these issues does — and does not — guarantee

**Will fixing everything in this report make the app 100% flawless and perfectly working? No.** Fixing these issues removes every *known* blocker — necessary, but not sufficient. Honest limits of this audit:

1. **Runtime behavior was not exercised.** This audit was static review plus unit tests. The Docker stack was never started, the E2E suite never executed, and no real call to Kimi/Mistral was made. Whole bug classes — timing races under real concurrency, memory leaks over days, DB behavior at scale, container networking quirks — only appear in a running system.
2. **The fixes themselves can introduce new bugs.** C1's transaction fix touches the most safety-critical write path in the codebase; it needs its own failing-before/passing-after tests.
3. **External dependencies are mocked everywhere.** Real provider latency, rate limits, and response drift are invisible to canned-mode tests. Green tests say nothing about live generation quality or cost.
4. **Coverage gaps remain.** `auth-context.tsx` and `generation-modal.tsx` have zero tests; fixes there are unguarded.
5. **Unknown unknowns.** Any audit samples reality; it does not exhaust it.

**A realistic path to high confidence:**
1. Fix in the recommended order, each with tests that fail before and pass after.
2. Gates green: `npm run lint && npm run typecheck && npm test` (root + backend) — currently red on `race.stories.test.ts`.
3. Run `npm run test:e2e` against the full stack (never executed during this audit).
4. Run at least one live-provider generation end-to-end (not canned mode).
5. Soak test: generate stories continuously for 24–48h on staging while watching the already-wired Prometheus/Grafana metrics.
6. Then production, with the verified-functional alert pipeline routing to a real receiver.

"100% flawless" is not a state software reaches; it is a discipline of catching what survives each stage.
